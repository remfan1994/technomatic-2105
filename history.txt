remfan1994:  takes more randomness than every 4 6 or 8 bars, I think you should try to keep it completely chaotic and unexpectable within multiples of 16 bars or whatever, reason being, predictability of style switching is like a type of stale also

chatgpt: I agree. If the goal is "music that can run for hours without becoming wallpaper," then fixed musical schedules are part of the problem.

Most procedural music systems do this:

* Every 4 bars: small variation.
* Every 8 bars: fill.
* Every 16 bars: section change.
* Every 32 bars: major change.

Humans learn those patterns surprisingly quickly. After twenty minutes, the listener can feel the machinery underneath.

A more interesting approach is hierarchical randomness:

* The beat has a current identity or "state."
* Changes occur according to probabilities rather than clocks.
* The probability of change slowly increases the longer nothing has changed.
* Some changes are tiny, some are dramatic.
* Changes can happen at unexpected moments, but not so often that the groove falls apart.

For example:

```
Current groove age: 47 seconds

Chance of tiny variation: 35%
Chance of fill: 12%
Chance of bass mutation: 8%
Chance of instrument swap: 2%
Chance of complete reinvention: 0.5%
```

Every beat or half-beat the engine rolls the dice.

Then you get behavior like:

* Groove lasts 20 seconds.
* Another lasts 3 minutes.
* Sometimes a fill appears unexpectedly.
* Sometimes the bassline mutates twice in ten seconds.
* Sometimes nothing happens for a while.

That feels more alive.

I would go further and avoid explicit "songs" entirely.

Think of it as a continuously evolving ecosystem:

* Drum organisms.
* Bass organisms.
* Melody organisms.
* Texture organisms.

Each has its own mutation rate and memory.

The kick pattern might survive for five minutes while the hats mutate constantly. The bassline may disappear and return later in a related form. A synth motif might reappear thirty minutes after first occurring.

At that point the app is no longer generating tracks. It is generating a musical environment.

The biggest challenge is actually the opposite of randomness: preserving enough memory that the result sounds intentional rather than like a casino. Pure randomness becomes noise. The engine needs to remember what it has done recently, avoid immediate repetition, and occasionally resurrect older ideas so the listener perceives continuity without predictability.

For a one-button app, most of the engineering effort would go into that memory system rather than the user interface. The UI might genuinely be nothing more than Play.

```kotlin
class AudioService : Service() {

    private lateinit var engine: NativeAudioEngine

    override fun onCreate() {
        super.onCreate()
        engine = NativeAudioEngine()
        startForeground(1, buildNotification())
    }

    override fun onStartCommand(intent: Intent?, flags: Int, startId: Int): Int {
        engine.start()
        return START_STICKY
    }

    override fun onDestroy() {
        engine.stop()
    }
}
```

The phone limits us on this:

```text
theme grammar
motif memory
arrangement logic
counter-melody rules
style identity
instrument role selection
long-term structure
```

Those are mostly decision systems, not expensive DSP systems.

So the honest answer is:

```text
sound-engine improvement room:
  moderate

composition-engine improvement room:
  very large

phone hardware obstacle:
  real, but not the main wall yet
```

The current engine already has usable synthesis. The next quality jump should not come mainly from adding twenty more oscillator tricks. It should come from making the machine compose better.

A useful formula:

```text
perceived musical quality =
  sound quality
  * rhythmic competence
  * melodic grammar
  * harmonic coherence
  * memory
  * surprise control
```

Right now, roughly:

```text
sound quality:          good
rhythm:                 good
macro randomness:       good
intra-song stability:   good
melody:                 acceptable but still mechanical
long-term memory:       early
harmony:                basic
counterpoint:           early
arrangement depth:      early to moderate
```

That means the remaining upside is substantial.

I would not describe it as:

```text
10 percent more possible
```

I would describe it more like:

```text
2x to 5x perceived musical improvement is still plausible
```

Maybe more, depending on how good the grammar layer gets.

Not because the phone can suddenly become a studio, but because the current weakest parts are algorithmic and structural. Algorithmic structure is cheap.

For example, this costs almost nothing:

```text
motif A appears
motif A repeats
motif A mutates
motif B answers
motif A returns later
```

That is musically powerful and computationally tiny.

This is expensive:

```text
64 high-quality oversampled synth voices
convolution reverb
neural melody generation
large animated editor
```

We do not need those.

The next improvement path should be:

```text
better thought, not heavier sound
```

More specifically:

1. Stronger melody grammar

The engine should stop thinking mainly in notes and start thinking in phrase shapes.

Bad model:

```text
pick next legal note
```

Better model:

```text
choose phrase contour
choose target note
move toward target
resolve or avoid resolving
repeat with variation
```

Example grammar:

```text
phrase has:
  start tone
  direction
  apex
  tension point
  resolution point
  rhythmic fingerprint
```

This is cheap to run. It is just integer and table logic.

2. Real theme hierarchy

Current-style generation:

```text
song
  motifs
```

Better:

```text
song
  themes
    motifs
      notes
```

A theme is not just a melody. It is a family of related shapes.

Example:

```text
theme:
  short rising figure
  then falling answer
  usually resolves to root or fifth
```

Then many phrases can be generated from the same theme without literally repeating.

This improves music more than adding another synth voice.

3. Harmony with intent

The app does not need complex jazz harmony. It needs functional gravity.

The listener should feel:

```text
home
departure
tension
return
```

Even primitive harmony can do this:

```text
i
bVI
bVII
i
```

or:

```text
root drone
fifth lift
flat seventh tension
root return
```

The engine needs to know where home is, not merely which notes are allowed.

4. Bass as grammar, not just low notes

Bass should be one of the main composers.

It can define:

```text
home
motion
pressure
release
section identity
```

A strong bassline can make simple melody sound intentional.

The bass should sometimes lead and the melody should answer. Other times melody leads and bass answers.

5. Counter-melody as conversation

The engine currently has layers. The next step is relationships between layers.

Bad version:

```text
lead plays
counter line also plays
```

Better version:

```text
lead asks
counter answers

bass states rhythm
arp imitates rhythm

melody rises
counter falls
```

Again, computationally cheap. Musically large.

6. Long-track memory

You like 20-minute tracks. That means the engine needs memory beyond the immediate phrase.

A 20-minute track should not be:

```text
one loop with variations for 20 minutes
```

It should be:

```text
minute 0:
  theme A born

minute 4:
  theme B appears

minute 9:
  theme A returns in altered form

minute 14:
  theme C grows from theme B

minute 18:
  theme A and B partially combine
```

This does not require much CPU. It requires saved symbolic state.

Memory is probably one of the biggest remaining improvements.

7. Instrument behavior, not just instrument count

You are right that more layers and more playing styles matter. But the important thing is not only:

```text
more instruments
```

It is:

```text
more ways for instruments to behave
```

For example, one synthetic voice can behave as:

```text
hook
answer
drone
sparkle
pulse
stab
swarm
echo
shadow
counter-line
```

That gives more musical diversity than simply adding 20 more timbres.

The engine should define:

```text
voice type
+
role
+
playing behavior
```

So an instrument is not just "bell." It is:

```text
bell as hook
bell as response
bell as distant echo
bell as rhythmic punctuation
```

That is a major depth multiplier.

8. Style families should become compositional laws

The internal genres should not be surface labels.

A style family should define:

```text
tempo habit
rhythm law
bass grammar
melody grammar
harmonic gravity
instrument role preference
density behavior
memory behavior
surprise behavior
```

So style A and style B do not merely use different sounds. They think differently.

That is how we avoid every song feeling like the same engine wearing different clothes.

9. Better arrangement devices, not human-copy "breakdowns"

I agree with dropping "breakdown" as a named inherited device.

Instead use invented devices, such as:

```text
suspension:
  time feels held while tonal elements hover

inversion:
  high and low roles swap

eclipse:
  main hook disappears behind texture, then re-emerges

crystallization:
  scattered notes gradually lock into a motif

fracture:
  phrase breaks into smaller rhythmic shards

magnet:
  all voices drift toward one pitch center

evaporation:
  density thins until only identity remains

surge:
  layers accumulate without becoming a standard drop

afterimage:
  old motif returns faintly in a different voice
```

These are more original than standard verse/build/drop/breakdown logic.

10. Quality control scoring

This is a big one.

The generator should not accept every composition it creates.

At composition birth, it can generate several candidates and score them.

Score for:

```text
melody memorability
rhythmic distinction
bass strength
harmonic clarity
instrument balance
theme contrast
avoidance of dead zones
avoidance of overbusy zones
```

Then choose the best candidate.

This can be done before playback starts or during transition, so it does not burden the audio callback.

This may produce a large improvement because the engine stops playing its bad first drafts.

The hardware-safe strategy is:

```text
generate symbolic candidates
score candidates
select one
render in realtime
```

Do not do:

```text
render audio candidates
analyze audio heavily
select one
```

Symbolic scoring is cheap.

The main hardware rule should be:

```text
spend intelligence at the composition layer
stay conservative at the audio layer
```

The audio callback must remain simple:

```text
no allocation
no file IO
no large loops
no UI work
no expensive random generation
```

But the composition engine can do much more outside the callback.

Practical ceiling:

```text
global instrument bank:
  can grow significantly

simultaneous active voices:
  should stay limited

composition complexity:
  can grow a lot

UI complexity:
  should shrink

song memory:
  can grow a lot

audio effects:
  should grow carefully
```

For the Stratus-class target, I would aim for:

```text
active musical lanes:
  about 8 to 16 most of the time

rare peak lanes:
  maybe 20 to 28 briefly

global instrument definitions:
  50 to 150 is fine if they are lightweight

active oscillator voices:
  controlled, not unlimited

heavy effects:
  minimal

composition state:
  large enough to remember long tracks
```

The phone can store lots of symbolic music. It cannot afford careless per-sample extravagance.

So yes, there is plenty of room left. But the path forward is not "make the synth huge." The path is:

```text
make the composer smarter
make instruments behave more musically
make styles think differently
make melodies have direction
make long tracks remember themselves
make the generator reject weak ideas
```

That is the next frontier.

```text

2. add candidate scoring so weak compositions are rejected before playback

3. add deeper theme/melody/harmony memory for 20-minute tracks
```

That is where I expect the largest gain per CPU cost.

chatgpt: Yes, the direction makes sense. The project should now be organized around what the engine does best rather than forcing conventional song and genre assumptions onto it.

## 1. Remove prefabricated melodic behavior

This is the most important change.

The current engine appears to have a large library of motif templates and transformations, but templates are still prefabricated musical shapes. Expanding from 20 to 256 variations reduces repetition statistically, but it does not eliminate the recognizable ancestry of those patterns.

That is especially noticeable in the bass because basslines are exposed repeatedly, occupy a narrow pitch range, and strongly define the identity of the music.

The target should become:

```text
Do not select a bassline.

Generate a bass grammar.
```

A generated bass grammar could contain:

```text
tonal center
allowed interval movements
rhythmic vocabulary
phrase length tendencies
rest behavior
repetition tolerance
relationship to percussion
relationship to the melodic voice
question behavior
answer behavior
cadence behavior
register boundaries
```

Then each bass phrase is constructed from those laws.

For example:

```text
phrase 1:
  establishes a subject

phrase 2:
  repeats its rhythmic identity with changed intervals

phrase 3:
  answers or contradicts it

phrase 4:
  resolves, suspends, or creates a new subject
```

That is different from:

```text
choose bass template 17
transpose it
rotate it
occasionally invert it
```

The vocal-like layer is a useful model. Its appeal comes from grammatical generation: related events form statements even when the exact statement has never existed before. Bass, melody, counter-line, and percussion should work through corresponding musical grammars.

The main principle should be:

```text
prefabricated grammar:
  acceptable

prefabricated sentences:
  remove
```

We can retain abstract rules such as question/answer, repetition/variation, tension/return, subject/predicate, and call/response. We should stop retaining fixed note strings that repeatedly surface.

## 2. How the current seed system probably works

Based on the architecture developed through these versions, the seed itself is probably not being continuously changed.

The likely model is:

```text
seed
  ->
initial composition state
  ->
deterministic internal evolution
```

During playback, the engine evolves:

```text
phrase index
theme state
instrument activity
motif transformation
arrangement device
harmonic state
random-number-generator state
```

The original seed remains the root input, while the pseudorandom generator advances internally.

So it may appear that the seed is mutating, but the more precise description is:

```text
the seed stays fixed;
the state produced from the seed evolves.
```

This distinction matters.

A 20-minute or infinite generation can remain reproducible if it begins from the same seed and advances through the same deterministic sequence. The app does not need to replace the seed every few minutes.

### Lock Sound versus Let Sound Mutate

This could be a meaningful control, but it should not mean locking the seed. The seed is already effectively locked during one generated stream.

It should mean:

```text
Let Sound Mutate:
  normal evolving generative state
  new phrases
  changing layers
  evolving instrumentation
  long-term transformations

Lock Sound:
  preserve the current musical identity
  continue generating within a narrower neighborhood
  prevent major palette, grammar, and structural mutations
```

A lock should not freeze the audio into a loop. That would defeat the app.

Instead:

```text
lock = constrain evolution
not = stop evolution
```

For example, Lock Sound could preserve:

```text
current tonal center
current bass grammar
current principal voice grammar
current instrument family
current rhythmic character
current density range
```

while still generating new notes and phrases.

That is potentially a strong main-screen feature:

```text
[ ] Lock Sound
```

or:

```text
Sound: Evolving / Locked
```

But it should only be implemented after verifying the native engine has a clean distinction between persistent composition identity and mutable phrase state. Otherwise it becomes another label disconnected from actual behavior.

## 5. Mix every channel 50 percent with unrestricted generation

This is sensible and probably fixes the genre problem more honestly than additional reset logic.

A channel would become:

```text
50% open generator
+
50% channel bias
```

Not a sealed genre.

For example:

```text
Soft Voltage =
  unrestricted musical generation
  biased toward smoother contours,
  lighter percussion,
  softer timbres,
  and lower dramatic pressure
```

Chrome Pulse:

```text
unrestricted musical generation
biased toward harder pulses,
clearer rhythmic edges,
higher activity,
and more metallic voices
```

This means the channel changes the probability field but does not replace the engine.

It also explains previous genre bleed more accurately. Some perceived overlap may not have been stale data. It may have been shared underlying generator character, because all styles were produced by one composer.

That is not necessarily a defect. It becomes intentional under this model:

```text
all channels belong to Technomatic 2105
```

They should differ, but they should not pretend to be unrelated human genres.

I would remove Pool and Hybrid if channels are always partially open-generator. They add conceptual complexity without much benefit.

A simpler model:

```text
Open Generator:
  100% unrestricted

Selected Channel:
  50% unrestricted
  50% selected channel character
```

One channel at a time.

That is cleaner and better aligned with the radio analogy.

## What the two current modes actually do

```text
finite piece length:
  generate sound A
  play it for the configured duration
  fade/conclude it
  generate a new seed
  play sound B
  repeat forever

Infinite:
  generate sound A
  never reach its ending
  never automatically generate sound B
  remain inside sound A indefinitely
```

This is explicit in `MusicEngine::onStep()`:

```cpp
if (!mInfinitePieceLength && !mExportSinglePieceMode) {
    ...
    beginTransition();
}
```

When the piece is finite, `beginTransition()` eventually reaches `switchToPendingStyle()`, which calls `generateSeededSong()` with a new seed. Playback does not stop between sounds.

Therefore:

```text
continuous playback + changing songs
```

already exists.

What needs modification is mostly the product model and UI, not the fundamental ability to keep playing.

## Recommended default playback model

I recommend:

```text
Default channel:
  Open Channel / No Genre

Default playback:
  Continuous Radio

Behavior:
  app plays indefinitely
  each sound has an internal lifetime
  new sounds are generated automatically
  playback itself never ends
```

The internal sound lifetime would no longer be presented as a normal listening control. It can be determined by the engine, probably with a broad distribution such as:

```text
ordinary sound:
  approximately 3-8 minutes

occasional short sound:
  approximately 1-3 minutes

occasional long sound:
  approximately 8-20 minutes
```

Those are not hard requirements yet. The important distinction is:

```text
session duration = infinite
sound duration = finite and engine-managed
```

Then the duration control in Advanced would apply only to OGG export.

The main screen would show:

```text
Elapsed: 2:41
```

meaning elapsed time in the current sound. It would reset when the engine begins the next generated sound.

## A separate "Hold Sound" function

The existing Infinite behavior is still useful, but it should not be called the default playback mode.

It can become:

```text
Hold Sound
```

Meaning:

```text
do not automatically replace this seed with a new seed
continue developing the current sound
```

However, there is an important limitation: the current engine does not substantially develop the melody or bass during an infinite sound. It changes sections, arrangements, note occurrence, ornaments, and drums, but the foundational melodic material remains fixed.

So there are two distinct improvements:

```text
Continuous Radio:
  already substantially implemented

One sound that evolves indefinitely:
  requires composition-level mutation work
```

I recommend making Continuous Radio the default and treating Hold Sound as an optional mode after we improve internal evolution.

## How the new bass generator should work

A bassline should be born from generated laws rather than stored notes.

For each new seed, generate a bass identity containing:

```text
rhythmic character
preferred note density
rest tendency
syncopation tendency
relationship to the kick
relationship to the chord
interval movement tendencies
register
question behavior
answer behavior
cadence behavior
repetition tolerance
mutation tolerance
```

Then generate phrases from it.

An example internal model:

```text
Bass grammar:
  begin near tonal home
  establish one recognizable rhythmic cell
  answer kick accents rather than copy all of them
  prefer small interval movement
  permit selected fourth/fifth movements
  approach the next chord near phrase endings
  resolve some phrases
  leave other phrases suspended
```

No stored sequence is required.

The result should be:

```text
bass phrase A:
  generated once

bass phrase A':
  recognizable variation of A

bass phrase B:
  answer or contrast

bass phrase A:
  deliberate return
```

The bassline would be original for the seed, yet recognizable inside that sound.

That is the essential principle:

```text
No prefabrication between sounds.
Deliberate recurrence within one sound.
```

A random music generator should not avoid all repetition. A song needs generated material that it can subsequently remember.

## The lead should be changed too

The lead is more diverse than the bass, but it is still template-based.

It starts with:

```text
20 stored sixteen-step melodic shapes
```

Those are transformed into nominally 256 template variants using operations such as:

```text
rotation
inversion
transposition
fragmentation
anchor alteration
reversal
```

This is substantially better than the five basslines, but all generated leads still descend from the same twenty ancestors. That explains why the music can feel varied while also becoming recognizable across long listening sessions.

The lead should therefore move to the same grammar model:

```text
generate:
  rhythmic cell
  contour
  interval vocabulary
  apex
  tension point
  cadence target
  phrase density
  call/answer relationship
```

Then create the primary motif from those rules.

The engine should retain:

```text
motif A
answer to A
variation of A
fragment of A
distant recall of A
```

But motif A itself should no longer come from a stored note array.

## The "vocal-like layer" clarification

There is not actually a separate vocal-language engine in the source with explicit:


What sounds vocal or rap-like emerges from several mechanisms acting together:


So we cannot literally copy a distinct vocal generator into the bassline. But we can formalize the property you are hearing:

```text

```

That is exactly what the bass and primary lead should use.


choose the strongest
store the accepted phrase

chatgpt: ## What "48 candidates" means

When Technomatic receives one visible seed, it does not immediately accept the first composition produced from that seed.

Instead, it creates 48 alternative symbolic drafts:

```text
candidate 0
candidate 1
candidate 2
...
candidate 47
```

Each candidate is a possible complete starting identity for the sound. The engine scores all 48 and keeps the highest-scoring one.

In algebraic form:

```text
S = user-visible seed
C_i = Generate(S, candidate_index=i, channel_state)

for i = 0 through 47:

Q_i = MusicalScore(C_i)
    + VarietyTerm(C_i)
    - RecentRepetitionPenalty(C_i)
    + SmallIndexBias(i)

winner = argmax(Q_i)

ActiveSound = C_winner
```

The source literally loops from candidate index 0 through 47, generates each draft, scores it, and copies the highest-scoring `Pattern` and `Composition` into the active engine.  

## They are 48 drafts, not 48 songs playing

The engine does not:

```text
render 48 audio files
listen to them
choose one
```

It does:

```text
generate 48 symbolic composition plans
mathematically evaluate them
render only the winner as audio
```

A candidate contains things such as:

```text
tempo
swing
tonal center
scale
harmonic path
drum pattern
bass grammar
main lead motif
hook motif
verse motif
answer phrases
counter-melody
arpeggio grammar
instrument palette
layer activity
memory behavior
evolution behavior
channel influence
```

This is why evaluating 48 candidates is computationally practical. Arrays of notes, gates, degrees, and parameters are cheap compared with generating and analyzing 48 actual audio recordings.

The project history shows that this symbolic quality-control search was gradually expanded as the composition engine developed, eventually reaching 48 drafts. 

## The candidates are siblings, not successive improvements

Candidate 44 is not candidate 43 with another mutation applied.

They are separate branches:

```text
                 visible seed S
                       |
       +---------------+---------------+
       |               |               |
    candidate 0     candidate 1      candidate 2 ...
       |               |               |
 complete draft    complete draft    complete draft
```

Candidate 0 uses the requested seed directly. Candidates 1 through 47 derive deterministic branch seeds by combining the requested seed with a different mathematical salt for each candidate index.

Conceptually:

```text
candidate_seed_0 = S

candidate_seed_i = S XOR salt(i)
```

The displayed seed remains `S`. The candidate index tells the engine which internal branch of that seed's possibility space was selected.

Current candidate generation is intended to be a pure function of:

```text
visible seed
candidate index
frozen channel configuration
```

One rejected candidate is not supposed to alter the next candidate. Recent-session memory affects the scoring, but it is not supposed to rewrite the candidate's actual notes. 

## What the mathematical judge measures

`scoreCurrentComposition()` does not merely count notes. It evaluates several categories.

### 1. Melodic substance

It examines:

```text
number of lead events
number of hook events
number of verse events
number of answer events
number of distinct scale degrees
melodic pitch span
```

A candidate with practically no melody is penalized.

A candidate whose melody remains trapped around one or two notes is also penalized.

### 2. Musical foundation

It examines:

```text
bass activity
bass development and answers
chord activity
```

This tries to ensure the composition has something supporting the lead.

### 3. Phrase grammar

It rewards things such as:

```text
recognizable repeated cells
direction changes
stable notes at important positions
contrast between statement and answer
rhythmic distinction between phrase halves
secondary-layer participation
```

This corresponds to the old principle:

```text
statement
answer
variation
return
```

rather than unrelated note events.

### 4. Long-form grammar

It includes generated values for:

```text
long-term memory
call and response
counterpoint
melodic gravity
hook stability
verse freedom
```

Thus the candidate judge prefers:

```text
a stable hook
+
a freer verse
+
related answers
```

over either total repetition or total randomness.

### 5. Instrument balance

It counts active musical lanes and compares them with a target appropriate to the sound's amount of space.

It penalizes:

```text
too few active layers
too many layers in a dense configuration
```

### 6. Bad-shape penalties

The current score reduces candidates for conditions including:

```text
too few lead notes
too few hook notes
too little bass
very narrow melodic span
too few distinct notes
only moving in one direction
too many large pitch leaps
weak hook stability
insufficient verse freedom
```

These terms are visible in the scoring implementation. 

## Recent-listening memory also affects the contest

Each candidate receives two fingerprints:

```text
overall pattern hash
melodic motif hash
```

If either fingerprint matches something in recent session memory, its score is reduced:

```text
recent overall pattern:
  -1.10

recent motif:
  -1.95
```

So the engine can reject a technically good candidate because it is too close to something recently heard.

There is also a deterministic variety term:

```text
0.00 through 1.00
```

and a much smaller index-dependent bonus on certain candidates.

Therefore, the winning candidate is not determined exclusively by the structural music score:

```text
final score =
  structural score
  + deterministic variety
  - repetition penalties
  + small branch bias
```

That introduces diversity among drafts with similar structural quality.

It can detect:

```text

weak bass
narrow melody
excessive leaps

```

It does not directly detect:

```text

the same "DOO, DOO" timbre becoming annoying
too much low-mid resonance
```

## Why exactly 48?

There is no musical theorem stating that 48 is ideal.

It is a search-width setting:

```text
more candidates:
  greater chance of finding a strong composition
  more CPU work when a new seed is generated

fewer candidates:
  faster generation
  greater chance of accepting a weak first draft
```

The important part is not the number 48 by itself. It is:

```text
candidate quality
*
scoring accuracy
*
candidate count
```

For example:

```text
48 strong and diverse drafts
+
accurate scoring
=
useful quality control
```

But:

```text
48 drafts sharing the same defect
+
a score that cannot perceive that defect
=
best-scoring draft still contains the defect
```

So the candidate system is useful, but it is not an artificial listener. It is a symbolic editorial filter. The musical generator creates the possibilities; the score chooses among them; the actual phone listening test still finds audible problems that the symbolic score does not yet understand.

## OGG and FLAC export

Advanced now contains:


Both exporters use the same snapshot model:

```text
1. Capture the current seed, candidate, Channel state, and generator data.
2. Render that sound independently from 0:00 for the selected duration.

4. Publish it under the public Music directory.
```

Live playback is not restarted, changed, or followed by the exporter.

```text

Music/<filename>.flac
```
